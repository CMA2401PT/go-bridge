# 阶段审查记录

用户要求每完成一部分，通过 byobu 中的 Claude 审查、讨论、修正后再提交。
审查对象是当前生成器与行为测试，不要求复制手写 expected 的实现。

## M3 前的架构讨论

Claude 建议用不透明 ID 代替地址句柄，并明确整体结果接管、批量缓冲区清零、转交后清空
原槽位。实现采用标准库 runtime/cgo.Handle，避免维护另一份 ID 表；所有权规则采纳。

类型操作采用各自独立的 ABI 计划（Slice，后续 Structure/Pointer），不把构造、缓冲区、
字段与函数统一塞进万能 Operation。共用的值转换与所有权仍由 ABI Type 描述。

类型闭包保留既定规则：只为 struct 自动补 *T；其他类型仅在已有 *T 时提供 ptr()。
推广字段属于 Go 事实，后续放到 gomodel，使用 Go 选择器规则处理未导出嵌入、遮蔽和歧义。

## M3：Ref 与 slice（审查通过）

Claude 用真实扩展复现了直接调用 `SliceInt.__new__` 后传参会访问未构造 C++ 内存的问题。
修正为统一的 checked_ref<T>：确认具体 Python 类型及对应 C++ holder 已构造之后才 cast，
函数参数、slice 接收者和批量元素均经过此入口。这里检查 Python 输入有效性，不恢复 Go panic。
已增加对应回归，正常 Go panic 的子进程测试仍保留。

同时加入模块专属 C++ 命名空间，验证两个生成库可在同一个 Python 进程中使用，跨模块
包装对象被拒绝，不交换 Go 句柄。04/05、字符串和嵌套元素、GC、批量错误释放、mypy 与
cgocheck2 的原生测试通过。

Claude 最终审查确认无阻塞。另采纳两项建议：具体类禁止 Python 子类化，确保 Self
声明与返回类型一致；Slice 禁用 reversed，避免它绕过不可迭代约定。

## M4a：Go 字段选择与有限类型补全（审查通过）

Claude 确认可见字段算法与 Ensure/补全边界没有阻塞问题。采纳来源可追溯性建议，
Type.Origin 记录首次依赖路径；文档明确补全原地修改模型，ptr() 看补全后的闭包。
补充提升字段跨深度胜出、中间嵌入指针、直接指针字段、不可支持的提升字段诊断、
直接字段与 Selectable 一致性，以及嵌套 struct 补全测试。

经过 nil 嵌入指针的字段仍照常暴露，实际访问按 Go 语义 panic；不隐藏字段，也不
给私有嵌入成员制造 Python 构造参数。后端以公开选择器名称访问字段。

## M4b/M5：对象后端与指针（审查通过）

Claude 在独立 index 快照上运行 vet、全部原生/cgocheck2/mypy 测试，并用独立包验证
跨包嵌入指针与提升方法、命名套命名、struct 视图/复制、命名指针、多级字段、Go 环、
非法 UTF-8 多返回值清理和命名冲突。结论无阻塞，句柄计数在错误路径和整套探测后均回到基线。

双方核对并修正了命名指针 `.value` 的 struct 视图：保存前必须转换成 Elem.Cell，
否则把 named pointer 放入 holder 会在后续 *T 断言处 panic。补充跨包回归。
另补全 Ensure 失败后不可复用模型的规则，后续调用保留首次错误，不返回半成品节点。

收尾的消费者检查发现两处 `.pyi` 名称问题：Classmethod/Property 函数遮蔽装饰器，
以及 Self/Cls 字段与构造声明的隐式接收者重名。装饰器改用 `_builtins` 限定，构造
声明使用 `_self`/`_cls`，保留原公开字段名与关键字。原生构造与 mypy 回归同时检查。

采纳审查的注释/排版建议；相等、deepcopy/pickle 的未支持边界写入验收文档，
不在本轮新增协议入口。Go panic 始终不由桥接层恢复。
